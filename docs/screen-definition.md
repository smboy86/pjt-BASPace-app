# 바스페이스 통합 기획 및 화면정의서

> 문서 버전: 3.30
>
> 최종 갱신일: 2026-08-19
>
> 관리 범위: 공통 · 고객 · 업체 담당자 · 관리자 화면
>
> 정본 원칙: 화면, 기능, 버튼, 권한, 상태, 내비게이션에 관한 결정은 이 문서를 기준으로 한다.

## 1. 문서 목적

이 문서는 바스페이스 앱의 제품 기획과 화면 정의를 한곳에서 확인하기 위한 단일 정본이다.
새 기능을 개발하거나 기존 기능을 수정할 때 구현 전에 관련 정의를 확인하고, 구현이 끝나면
실제 동작에 맞게 이 문서를 함께 갱신한다.

`_workspace/plan/prd.md`, `_workspace/design/design-system.md`, `docs/specs/`는 배경 자료와
작업 이력을 제공한다. 화면 관련 내용이 서로 다르면 이 문서를 우선하며, 아직 결정되지 않은
내용은 임의로 현재 기능처럼 기록하지 않고 `계획` 또는 `검토 필요`로 표시한다.

### 1.1 이 문서만으로 확인할 수 있어야 하는 정보

- 앱의 목적, 사용자 역할, 핵심 업무 흐름
- 역할별 전체 화면 목록과 구현 상태
- 각 화면의 목적, 진입 조건, 주요 표시 정보
- 버튼·입력·선택 요소의 동작과 이동 경로
- 로딩·빈 상태·오류·완료·권한 제한 상태
- 실제 서버 연동 여부와 로컬 프로토타입 여부
- 아직 구현되지 않은 화면과 다음 개발 범위

### 1.2 상태 표기

| 상태 | 의미 |
|---|---|
| `구현` | 현재 코드에 화면과 핵심 동작이 존재한다. |
| `부분 구현` | 화면은 존재하지만 일부 역할, 데이터, 상태 또는 동작이 빠져 있다. |
| `로컬 구현` | 화면과 동작은 존재하지만 서버에 저장되지 않고 메모리 상태만 사용한다. |
| `계획` | 제품 범위에는 포함되지만 현재 화면 코드가 없다. |
| `보류` | 방향 결정이나 별도 승인이 필요하다. |

## 2. 제품 정의

### 2.1 한 줄 설명

바스페이스는 고객의 욕실 조건·사진·제품 선택을 구조화하고, 관리자 배정 후 고객과 업체
담당자가 여러 차례 견적과 코멘트를 주고받을 수 있게 하는 욕실 리모델링 견적 협업 앱이다.

### 2.2 핵심 범위

- 고객 이메일 가입·확인·로그인
- 고객의 욕실 견적 요청 작성과 사진 선택
- 관리자의 업체 및 특정 담당자 배정
- 업체 담당자의 견적 작성·수정 버전 발송
- 고객과 업체 담당자의 요청별 상담 타임라인
- 고객의 최종 견적 컨펌
- 업체 담당자 또는 관리자의 시공 완료 처리
- 관리자의 업체·카탈로그·가격표 관리

### 2.3 비범위

- 앱 내 결제와 계약금
- 전자계약과 세금계산서
- 공개 업체 디렉터리와 리뷰 랭킹
- AR·3D 욕실 렌더링
- 전체 시공 일정·공정·A/S 관리
- 광고, 구독, 인앱결제, 보상형 잠금 해제

### 2.4 역할과 권한

| 역할 | 코드 | 주요 권한 | 현재 앱 지원 상태 |
|---|---|---|---|
| 고객 | `customer` | 가입, 요청 작성, 요청·견적 열람, 코멘트, 최종 컨펌 | 인증 구현, 요청·상담은 로컬 구현 |
| 업체 담당자 | `partner_staff` | 배정 견적 열람, 진행·취소 응답, 시공 완료, 코멘트, 견적 버전 작성·발송 | 인증·업체 연결·배정 견적 조회와 진행·완료 응답 구현     |
| 관리자      | `admin`         | 요청 모니터링, 업체·담당자 배정, 시공 완료, 업체 승인, 카탈로그 관리   | 인증, 전체 요청 조회·완료 처리, 업체·카탈로그 관리 구현 |

인증 API는 활성 상태의 `customer`, `partner_staff`, `admin` 프로필을 허용한다.
`customer`는 고객 탭, `partner_staff`는 업체 담당자 홈, `admin`은 관리자 운영 홈으로
진입한다. 공개 회원가입은 항상 `customer` 프로필만 생성하며 관리자와 업체 담당자는
운영자가 생성·연결한다.

### 2.5 핵심 업무 흐름

```text
고객 가입 및 이메일 확인
→ 고객 로그인
→ 견적 요청 작성 및 제출
→ 관리자 초기 견적 금액 조정
→ 고객 조정 견적 확인
→ 관리자 업체·담당자 배정
→ 업체 담당자 배정 견적 확인 및 진행 또는 취소
→ 업체 담당자 최초 견적 발송
→ 고객 질문 또는 수정 요청
→ 업체 담당자 수정 견적 발송
→ 고객 최종 컨펌
→ 오프라인 계약·시공 상담으로 전환
```

`최종 컨펌`은 계약 또는 결제를 의미하지 않는다.

### 2.6 견적 요청 상태

| 상태 | 화면 표시 | 의미 | 변경 주체 |
|---|---|---|---|
| `draft` | 작성 중 | 고객이 요청을 작성하는 상태 | 고객 |
| `submitted` | 매칭 대기 | 요청 제출 후 관리자 배정을 기다리는 상태 | 고객 |
| `quote_adjustment` | 견적 조율 | 관리자가 초기 견적 금액을 조정하고 고객 확인 또는 업체 배정을 기다리는 상태 | 관리자·고객 |
| `matched` | 업체 매칭 완료 | 업체 또는 담당자가 배정된 상태 | 관리자 |
| `in_consultation` | 견적 협의 중 | 코멘트 또는 견적을 주고받는 상태 | 고객·업체 |
| `final_quote_sent` | 최종 견적 도착 | 업체가 최종 견적을 발송한 상태 | 업체 |
| `confirmed` | 최종 컨펌 | 고객이 최종 견적을 확인한 상태 | 고객 |
| `closed`           | 시공 완료      | 배정 업체가 승인한 시공중 견적의 시공이 완료된 상태                         | 관리자·업체 |
| `cancelled` | 취소 | 배정 업체가 진행 불가를 확정해 견적 진행이 종료된 상태 | 업체 |

### 3.5 현재 실행 가능한 범위

```text
고객 회원가입·이메일 확인·로그인
→ Supabase 견적 요청 제출
→ Supabase 나의 견적 목록과 요청·선택 상세 확인 및 상담 코멘트 작성
→ 관리자 조정 견적 확인

관리자 로그인
→ 관리자 운영 홈
→ 전체 고객 견적 요청 상태별 조회
→ 신규 견적 가격 조정
→ 고객 확인 후 업체 배정
또는 업체 목록 조회 → 업체 추가 또는 업체 상세 확인
또는 견적 옵션 목록 조회 → 견적 옵션 상세 수정

업체 담당자 로그인
→ 업체 담당자 홈
→ 배정 견적서 확인
→ 배정 견적 상세에서 진행 또는 취소 응답
→ 시공중 견적의 시공 완료 처리

관리자
→ 견적 진행 상세에서 시공 완료 처리
```

| 기능 영역 | 현재 데이터 연동 |
|---|---|
| 고객 가입·로그인·이메일 재전송·세션 복원·로그아웃 | 실제 Supabase 및 SecureStore |
| 요청 생성·목록·선택 상세 | 실제 Supabase 및 TanStack Query, 화면 협업 상태는 Zustand 인메모리 |
| 사진 | 기기 로컬 URI, 원격 업로드 없음 |
| 상담 메시지                                       | 실제 Supabase 및 TanStack Query                                           |
| 견적 버전·컨펌 | Zustand 인메모리, 견적 생성 UI 없음 |
| 업체 배정                                         | 실제 Supabase 관리자 선택 모달·RPC 및 TanStack Query                      |
| 업체 진행·취소 응답과 시공 완료                   | 실제 Supabase 제한 RPC 및 TanStack Query                                  |
| 관리자 견적 관리 | 실제 Supabase 전체 요청·고객·배정 업체 조회 및 TanStack Query |
| 업체 관리 | 실제 Supabase 목록·등록·상세 및 비공개 Storage 사업자등록증 |
| 업체 담당자 계정 | 관리자 전용 Edge Function에서 Auth 사용자·프로필·업체 대표 멤버 연결 |
| 견적 옵션 관리 | 실제 Supabase 카테고리 목록·상세 수정 및 카테고리별 복수 제품 이미지 관리 |
| 앱 재시작 후 요청 복원 | Supabase에서 고객 본인의 요청·선택 스냅샷 재조회 |
| 앱 재시작 후 견적 버전 복원                       | 지원하지 않음                                                             |
| 역할별 진입 | 고객·업체 담당자·관리자 지원 |
| 회원 탈퇴 | 미구현 |

업체 견적 버전 작성·발송, 실제 다회차 견적 수정과 최종 견적 도착은 현재 UI만으로
수행할 수 없다. 고객 요청부터 관리자 조정·배정, 업체 진행 승인과 시공 완료까지의 상태
전이는 실제 Supabase에 저장된다.

## 4. 공통 화면 정의

### COM-001 앱 시작·세션 확인

| 항목 | 정의 |
|---|---|
| 상태 | `부분 구현` |
| 구현 파일 | `app/index.tsx`, `app/_layout.tsx` |

| 목적 | 앱 시작 시 저장된 Supabase 세션과 사용자 프로필을 확인하고 적절한 화면으로 보낸다. |
| 진입 | 앱 실행, 딥링크 진입, 세션 상태 변경 |
| 데이터 | Supabase Auth 세션, `profiles` 사용자 프로필, SecureStore 세션 저장소 |

주요 상태:

- 확인 중: 로딩 표시와 `로그인 정보를 확인하고 있어요.` 문구를 표시한다.
- 비로그인: 로그인 화면으로 교체 이동한다.
- 로그인: 프로필 역할에 따라 고객 탭, 업체 담당자 홈 또는 관리자 운영 홈으로 교체 이동한다.
- 확인 실패: 네트워크 안내와 `다시 시도` 버튼을 표시한다.

| 액션 | 조건 | 결과 |
|---|---|---|
| 다시 시도 | 세션 확인 오류 | 세션과 사용자 프로필을 다시 조회한다. |
| 자동 로그인 이동 | 유효 세션 없음 | `/(auth)/login`으로 이동한다. |
| 고객 홈 이동 | 활성 고객 세션 존재 | `/(tabs)/home`으로 이동한다. |
| 업체 담당자 홈 이동 | 활성 업체 담당자 세션 존재 | `/(partner)/dashboard`로 이동한다. |
| 관리자 홈 이동 | 활성 관리자 세션 존재 | `/(admin)/dashboard`로 이동한다. |
| Android 앱 종료 안내 | 고객 홈, 업체 담당자 홈 또는 관리자 운영 홈에서 하드웨어 뒤로가기를 처음 누름 | 옅은 네이비 배경의 `한번 더 뒤로가기를 눌러 앱을 종료할 수 있어요` 토스트를 2초 동안 표시하고 앱을 유지한다. |
| Android 앱 종료 | 종료 안내 토스트를 표시한 뒤 2초 이내에 하드웨어 뒤로가기를 다시 누름 | 앱을 종료한다. 2초가 지나면 승인 상태를 해제하고 다음 뒤로가기에서 안내 토스트부터 다시 표시한다. |

제약:

- 활성 고객·업체 담당자·관리자 프로필만 앱 세션으로 인정한다.
- 인증 화면에 로그인 사용자가 진입하면 해당 역할 홈으로 돌려보낸다.
- 고객·업체 담당자·관리자가 다른 역할의 화면 그룹에 접근하면 자신의 역할 홈으로 돌려보낸다.
- 인증되지 않은 사용자가 보호 화면에 진입하면 로그인으로 보낸다.
- Android 하드웨어 뒤로가기 종료 보호는 고객 홈, 업체 담당자 홈, 관리자 운영 홈에서 적용한다. 고객의 견적요청·나의견적·알림·설정 탭 최상위에서는 홈으로 이동하고, 고객 상세·입력 화면에서는 직전 화면으로 돌아가며 직전 화면 이력이 없으면 홈으로 이동한다.
- iOS와 웹에는 Android 하드웨어 뒤로가기 종료 보호를 적용하지 않는다.
- 다른 고객 탭에서 홈으로 이동한 Android 뒤로가기 입력은 홈의 종료 대기 첫 입력으로 계산하지 않는다.
- 업체 담당자·관리자 홈의 기존 종료 정책은 유지한다.

### COM-002 로그인

| 항목 | 정의 |
|---|---|
| 상태 | `부분 구현` |
| 구현 파일 | `app/(auth)/login.tsx` |
| 대상 역할 | 고객·업체 담당자·관리자 |
| 목적 | 이메일·비밀번호, Kakao 또는 Google 계정으로 사용자 인증을 수행한다. |
| 입력 | 이메일, 비밀번호 |
| 데이터 | Supabase Auth 및 `profiles` |

| 액션 | 조건 | 결과 |
|---|---|---|
| 로그인 | 이메일·비밀번호 입력 완료 | 활성 고객은 `/(tabs)/home`, 활성 업체 담당자는 `/(partner)/dashboard`, 활성 관리자는 `/(admin)/dashboard`로 이동한다. |
| 카카오로 계속하기 | 인증 처리 중이 아님 | Google 버튼 위에 표시한다. 시스템 브라우저에서 Kakao 계정을 인증하고 신규 Kakao 사용자는 고객 프로필을 생성한 뒤 `/(tabs)/home`으로 이동한다. |
| Google로 계속하기 | 인증 처리 중이 아님 | 시스템 브라우저에서 Google 계정을 선택하고 신규 Google 사용자는 고객 프로필을 생성한 뒤 `/(tabs)/home`으로 이동한다. |
| 고객 회원가입 | 로그인 처리 중이 아님 | `/(auth)/signup`으로 이동한다. |
| 임시 계정 배지 | 개발 모드이며 로그인 처리 중이 아님 | 이메일 라벨 오른쪽의 `고객`, `업체`, `관리자` 배지를 선택하면 해당 가데이터 계정의 이메일과 비밀번호를 입력란에 채운다. 로그인 요청은 별도로 로그인 버튼을 눌렀을 때만 실행한다. |

상태와 검증:

- Android에서는 시스템 `adjustResize`로 로그인 콘텐츠 영역을 줄이고, 키보드 표시가 완료된
  뒤 이메일·비밀번호 중 포커스된 입력란의 위치를 다시 측정해 키보드 위로 자동 이동한다.
- 키보드가 열린 상태에서 다른 입력란으로 포커스를 바꾸면 새 입력란이 보이도록 다시 이동한다.
- 이메일 키보드의 `다음`을 누르면 비밀번호 입력란으로 포커스를 이동한다.
- 이메일 또는 비밀번호가 비어 있으면 입력 요청 오류를 표시한다.
- 이메일 형식이 잘못되면 올바른 주소 입력 오류를 표시한다.
- 로그인 요청 중에는 입력과 버튼을 비활성화하고 `로그인 중`을 표시한다.
- Google 인증 요청 중에는 모든 인증 입력과 버튼을 비활성화하고 `Google 로그인 중`을 표시한다.
- Kakao 인증 요청 중에는 모든 인증 입력과 버튼을 비활성화하고 `카카오 로그인 중`을 표시한다.
- Kakao 계정 인증을 취소하면 `카카오 로그인이 취소되었습니다.`를 표시하고 현재 화면을 유지한다.
- Kakao 인증 실패 또는 앱 리디렉션 코드 누락 시 안전한 사용자용 오류와 재시도 가능 상태를 표시한다.
- Google 계정 선택을 취소하면 `Google 로그인이 취소되었습니다.`를 표시하고 현재 화면을 유지한다.
- Google 인증 실패 또는 앱 리디렉션 코드 누락 시 안전한 사용자용 오류와 재시도 가능 상태를 표시한다.
- 인증 실패, 이메일 미확인, 비활성 계정, 네트워크 오류는 사용자용 문구로 표시한다.
- 고객은 직접 가입할 수 있고 업체 담당자와 관리자는 운영자 생성 계정으로 참여한다는
  안내를 표시한다.
- 임시 계정 배지는 `__DEV__`에서만 노출하고 선택한 계정 정보는 컴포넌트 입력 상태에만
  반영하며 별도로 저장하지 않는다.

구현 범위:

- Kakao·Google OAuth는 Supabase PKCE와 `baspace://auth/callback` 리디렉션을 사용한다. Expo 개발
  환경에서는 `Linking.createURL('auth/callback')`이 만든 현재 실행 환경의 동등한 URL을 사용한다.
- OAuth 세션은 기존 Supabase SecureStore 어댑터에 저장하고 완료 직후 Google provider와
  활성 고객 프로필을 재검증한다.
- 데이터베이스는 기존 이메일 identity가 있는 사용자에게 Kakao·Google identity가 자동 연결되는
  것을 차단한다. 업체 담당자·관리자 프로필은 소셜 인증으로 앱에 진입할 수 없다.

미구현:

- 업체 담당자 앱 화면 진입
- 비밀번호 찾기
- 다른 SNS 로그인은 소요 시간 검토 후 결정한다.

출시 전 제거:

- 임시 계정 배지와 가데이터 계정 정보는 스토어 배포 전에 로그인 화면에서 삭제한다.

- 같은 인증 코드를 화면 생명주기 안에서 중복 교환하지 않는다.
- Google·Kakao·고객 이메일 확인 이외의 provider, 업체 담당자·관리자 프로필, 비활성 고객은 세션을 정리하고
  로그인을 거절한다.
- 오류 상세, 인증 코드, access token, refresh token은 화면이나 로그에 노출하지 않는다.
- 콜백 완료 후 세션은 기존 Supabase SecureStore 어댑터에 저장한다.

| 고객 | 기존·조정 견적 비교 | 항상 | 조정 전에는 `기존 견적`과 원금액만 표시하고, 조정 후에는 기존 금액을 작은 회색 취소선으로 표시한 뒤 관리자 조정 금액과 증감 방향·차액을 표시한다. |
| 고객 | 조정 견적 최종 확정 | `quote_adjustment`, 조정 금액 존재, 미확정 | 서버에 고객 확인 시각을 저장하고 확인 완료 상태를 표시한다. |
| 관리자 | 현재 견적 금액 | 항상 | 조정 전에는 선택 스냅샷 합계, 조정 후에는 최신 조정 금액을 크게 표시한다. |
| 관리자 | 수정 견적 금액 입력 | 요청이 `submitted` | 원 단위 정수를 입력한다. |
| 관리자 | 수정 견적 사유 입력 | 요청이 `submitted` | 금액 입력 아래에서 공백 제외 1자 이상 500자 이하의 텍스트를 입력한다. |
| 관리자 | 견적 조정 | 유효 금액·사유 입력, 저장 중이 아님 | 조정 금액·사유·관리자·조정 시각을 한 번에 저장하고 요청 상태를 `quote_adjustment`로 변경한다. |
| 관리자 | 공사 가능 날짜 입력·변경 | `submitted` 또는 고객 미확인 `quote_adjustment`, 내일 이후 날짜를 현재 관리자 입력 날짜와 다르게 선택 | 관리자 전용 RPC가 현재 값을 변경하고 이전값·새 날짜·관리자·변경 시각을 이력으로 저장한다. |
| 업체 담당자 | 현재 견적 금액 | 배정된 요청 열람 가능 | 조정 전에는 선택 스냅샷 합계, 조정 후에는 최신 조정 금액을 읽기 전용으로 표시한다. |
| 업체 담당자 | 견적 확인 및 진행 | 현재 업체 배정이 `assigned`, 요청이 `matched` 또는 `in_consultation` | 서버에서 배정을 `accepted`, 요청을 `in_consultation`으로 변경한다. |
| 업체 담당자 | 진행 불가 | 현재 업체 배정이 `assigned`, 요청이 `matched` 또는 `in_consultation`, 확인 메시지 승인 | 서버에서 현재 배정을 `declined`로 변경하고 남은 활성 배정이 없으면 요청을 `cancelled`로 변경한다. |
| 업체 담당자 | 시공 완료           | 현재 업체 배정이 `accepted`, 요청이 `in_consultation` 또는 `final_quote_sent`          | 서버에서 요청을 `closed`로 변경하고 업체 완료 견적 탭으로 이동시킨다.                             |
| 관리자      | 시공 완료           | 요청이 `in_consultation` 또는 `final_quote_sent`                                       | 서버에서 요청을 `closed`로 변경하고 관리자 완료·종료 탭으로 이동시킨다.                           |

규칙:

- 공통 UI와 역할 분기는 하나의 widget에서 관리하고 경로 파일은 역할과 요청 ID만 전달한다.
- 원 견적 금액은 서버에 저장된 선택 스냅샷 단가 합계이며 클라이언트 입력값을 신뢰하지 않는다.
- 관리자의 초기 견적 조정은 `submitted` 상태에서 한 번만 가능하다. `quote_adjustment`로
  전환된 뒤에는 고객 확인 전후와 관계없이 금액·사유 입력과 조정 버튼을 비활성화한다.
- 수정 견적 사유는 조정 금액과 같은 서버 트랜잭션으로 한 번만 저장한다. 저장된 사유는
  고객과 배정 업체의 상세 화면에서 수정 견적 금액 바로 아래에 읽기 전용으로 표시한다.
- 고객 상세의 견적 비교 카드는 조정 금액이 없으면 `기존 견적` 원금액만 크게 표시한다. 조정
  금액이 있으면 기존 금액을 작은 회색 취소선으로 낮추고 `관리자 조정 견적` 금액을 강조한다.
  기존 금액과의 차액은 `기존 견적` 섹션의 오른쪽에 기존 금액과 같은 글자 크기로 배치한다.
  상승·하락 아이콘과 부호가 포함된 원 단위 금액만 표시하고 별도의 증감 설명 문구나 라벨은
  표시하지 않는다. 차액이 0원이면 중립 아이콘과 `0원`을 표시한다.
- 고객이 제출한 최초 `공사 희망 날짜`는 최초 일정 변경 이력의 `previous_schedule`로 유지해
  표시한다. 변경 이력이 없으면 요청의 `desired_schedule`을 고객 희망 날짜로 표시한다.
- 관리자는 `submitted` 또는 고객이 아직 확인하지 않은 `quote_adjustment`에서만 내일 이후
  `공사 가능 날짜`를 입력·변경할 수 있고 변경 사유는 입력하지 않는다. 고객 확인 완료
  (`adjustment_confirmed_at` 존재) 및 `matched` 이후 단계에서는 날짜 입력·변경 버튼을 숨기고
  저장을 실행하지 않는다. 같은 날짜 저장은 이력을 추가하지 않는다.
- 고객은 제출된 요청의 날짜를 직접 변경할 수 없다. 관리자 입력값은 최신 일정 변경 이력의
  `new_schedule`로 표시하고 전체 변경 이력은 서버에 누적 보존한다.
- 철거 추가 비용은 요청의 만원 단위 스냅샷에 `10,000`을 곱해 표시·합산한다. 선택 제품
  스냅샷 합계에 한 번만 더하며, 덧방에는 비용을 더하지 않는다.
- 고객 확인은 `quote_adjustment` 상태를 유지한다. 이후 업체 배정이 완료될 때 `matched`로
  전환한다.
- 이 초기 조정 금액은 업체 배정 후 생성되는 `quotes` 견적 버전과 구분한다.
- 관리자 모드에는 코멘트 입력과 고객용 최종 컨펌 버튼을 표시하지 않는다.
- 업체 모드에는 관리자 전용 견적 금액 입력·조정과 고객용 확정·코멘트 입력을 표시하지 않는다.
- `시공 완료`는 클라이언트 직접 갱신이 아니라 권한과 현재 상태를 재검증하는 공통 RPC로만
  저장한다. 완료 후 동일 요청에 대한 중복 완료 요청은 서버에서 거부한다.
- 업체 배정 전 고객·관리자 코멘트는 `consultation_messages.assignment_id = null`인 요청 단위
  메시지로 저장한다. 요청 소유 고객과 관리자뿐 아니라 해당 요청에 배정되어 상세 열람 권한이
  있는 활성 업체 담당자도 배정 전후의 전체 요청 단위 상담 타임라인을 조회할 수 있다.
- 코멘트 등록만으로 요청 상태를 변경하지 않으며 현재 `submitted` 또는 `quote_adjustment`
  상태를 유지한다.

검증과 상태:

- 조정 금액은 0원 이상 1조 원 이하의 정수이며 수정 견적 사유는 공백 제외 1자 이상
  500자 이하의 텍스트다.
- 날짜 변경은 기기 로컬 기준 내일 이후 `YYYY-MM-DD`만 선택하고 서버는 서울 날짜 기준으로
  같은 조건을 다시 검증한다.
- 요청 로딩, 조회 실패·재시도, 요청 없음, 상담 타임라인 로딩·실패, 코멘트 저장 중·실패,
  조정 저장 중·실패·완료, 날짜 변경 저장 중·실패·완료, 고객 확인 중·실패·완료, 시공 완료
  저장 중·실패·완료를 제공한다.
- 고객·관리자는 기존 역할 권한으로, 업체 담당자는 연결된 업체의 배정 범위에서만 RLS와
  제한 조회·응답 RPC 검증을 통과할 수 있다.

검증과 상태:

- 시공 타입을 선택하지 않으면 공사 조건 섹션과 선택 카드에 오류를 표시한다.
- 공사 희망 날짜를 선택하지 않았거나 제출 시점에 내일 이전이면 공사 조건 섹션과 날짜 버튼에
  오류를 표시한다.
- 기본 주소가 비어 있으면 기본 조건 섹션에 빨간 오류 라벨을 표시한다.
- 희망 예산을 선택하지 않으면 기본 조건 섹션에 빨간 오류 라벨을 표시한다.
- 체크한 옵션에 제품이 선택되지 않으면 중요 선택 옵션 섹션과 해당 옵션에 빨간 오류 라벨을 표시한다.
- 옵션 로딩 중에는 로딩 안내를 표시하고 제출을 비활성화한다.
- 옵션 조회가 실패하면 오류 안내와 `다시 시도` 버튼을 표시한다.
- 확대 이미지를 불러오는 동안 로딩 상태를 표시하고 실패하면 이미지 오류 안내를 표시한다.
- 이미지가 없는 제품은 상세보기 아이콘을 표시하지 않는다.
- 제출 중에는 입력과 제출 버튼의 중복 동작을 막는다.
- 서버 제출 실패 시 입력을 유지하고 제출 섹션에 재시도 가능한 오류를 표시한다.
- 제출 성공 시 `submitted` 상태로 저장하고 관리자의 확인을 기다린다는 완료 모달을 표시한다.
- 사진이 이미 5장이면 최대 등록 수 안내를 표시한다.
- 사진 권한이 거부되면 권한 필요 안내를 표시한다.
- 로그인 사용자가 없으면 재로그인 안내 후 로그인 화면으로 이동한다.
- 사진은 선택 사항이며 0장으로 제출할 수 있다.

현재 제약:

- 요청 본문과 제품 선택 스냅샷은 Supabase에 저장하지만 사진 URI는 같은 세션의 메모리에만 유지되며 로그아웃·앱 재시작 후 사라진다.
- 파일 크기와 JPG·PNG·HEIC 형식 검증은 화면에 연결되지 않았다.
- 상세 주소는 선택 사항이다.
- 고객은 옵션을 체크하지 않고 제출할 수 있다.
- 완료 모달은 뒤로가기 요청으로 닫히지 않고 `확인`을 눌러야 한다.

업무 규칙:

- `철거` 선택 시 관리자 `시공 타입 금액 설정`의 현재 값을 만원 단위 정수로 요청에
  스냅샷 저장한다. 기본 설정값 `150`은 화면과 합계에서 `150만원`으로 변환한다.
- `덧방`은 시공 타입만 저장하고 추가 비용 스냅샷은 저장하지 않는다. 설정값을 변경해도 이미
  제출된 요청의 스냅샷은 바뀌지 않는다.
- 기능 적용 시점에 이미 존재하는 철거 요청은 기본값 `150`으로 한 번 백필하고 덧방 요청은
  비용 스냅샷을 비운다.

계획·검토 필요:

- 고객 선택용 상위 카테고리는 원격에 적용된 목표 8개 구성을 사용한다. 신규 `수전 / 유가`,
  `젠다이 / 조적 파티션`, `천장재 / 조명 / 환풍기`, `줄눈`은 관리자가 제품을 등록하기 전까지
  제품이 없는 카테고리로 표시된다.
- `CUS-008` 알림 모델이 구현되면 일정 변경 인앱 알림을 추가하고 푸시 알림은 후속 범위로 둔다.

- 요청 로딩: 고객 요청 Query가 완료될 때까지 로딩 안내를 표시한다.
- 요청 조회 실패: 네트워크 안내와 다시 시도 액션을 표시한다.
- 요청 없음: 찾을 수 없음 안내와 목록 복귀 버튼을 표시한다.
- 견적 없음: 업체가 리포트를 검토 중이라는 빈 상태를 표시한다.
- 메시지 없음: 별도 빈 상태 문구 없이 입력 영역만 표시한다.
- 코멘트 저장 중에는 입력과 전송 버튼을 비활성화하고, 실패하면 입력 내용을 유지한 채

현재 제약:

- 앱 내부에 견적 생성 화면과 초기 견적 데이터가 없어 정상 사용자 흐름으로는 견적 카드와
  최종 컨펌 버튼에 도달할 수 없다.
- 화면에 여러 견적 카드가 있어도 모든 컨펌 버튼은 정렬상 최신 견적을 확정한다.
- 최종 견적 상태인지 확인하지 않고 `confirmed`가 아닌 모든 견적에 컨펌 버튼을 표시한다.
- 고객 요청은 RLS와 고객 ID 조건으로 조회하며, Query 결과에 없는 요청 ID는 찾을 수 없음으로 처리한다.
- 조정 견적 금액과 고객 확인은 서버에 저장하고, 업체 견적 버전·메시지·기존 최종 컨펌은
  아직 로컬 상태다.
- 코멘트는 모두 `수정 요청` 유형으로 저장되며 질문·확인 선택 UI는 없다.
- 사진은 개수만 표시하고 이미지 미리보기는 제공하지 않는다.
- 최종 컨펌 완료 안내는 네이티브 `Alert`를 사용한다.

| 목적      | 현재 로그인 계정 정보를 확인하고 이름·연락처를 수정한다. |
| 데이터    | Supabase Auth 이메일, `public.profiles` 본인 행          |

진입과 이탈:

- `CUS-007 설정`의 `로그인 정보` 행을 누르면 진입한다.
- 상단 `설정` 뒤로가기 버튼과 시스템 뒤로가기는 직전 화면으로 돌아간다. 직전 화면 이력이 없으면 `CUS-010 고객 홈 랜딩`으로 이동한다.
- 저장 완료 후에는 현재 화면에 머무르며 뒤로가기로 이탈할 수 있다.
- 고객 탭 바에는 별도 탭으로 노출하지 않는다.

표시·입력 정보:

- 이메일: 현재 Supabase Auth 이메일을 읽기 전용으로 표시한다.
- 이름: 현재 `profiles.display_name`을 표시하며 2자 이상 80자 이하로 수정할 수 있다.
- 연락처: 현재 `profiles.phone`을 표시한다. 값이 있으면 숫자 10~11자리만 허용하고,
  하이픈은 입력·저장 시 제거한다. 비워서 저장하면 `null`로 저장한다.

버튼·액션:

- `변경사항 저장`은 유효한 이름과 연락처가 있고, 최초 조회값과 달라졌을 때만 활성화한다.
- 저장 시 현재 인증 고객의 `display_name`, `phone`만 Supabase에 갱신한다.
- 저장 성공 시 TanStack Query 캐시와 인증 메모리 상태를 갱신해 화면과 설정 요약에 최신 이름을
  즉시 반영하고 완료 안내를 표시한다.

상태:

- 조회 중에는 로딩 안내를 표시한다.
- 조회 실패 시 네트워크 안내와 `다시 시도` 버튼을 표시한다.
- 저장 중에는 입력, 현재 화면 뒤로가기, 저장 버튼의 중복 실행을 막고 진행 상태를 표시한다.
  다른 고객 탭으로 이동해도 진행 중인 저장 요청과 완료 후 캐시 갱신은 유지한다.
- 검증 실패는 해당 입력 아래에 안내하며, 저장 실패 시 입력값을 유지하고 재시도 안내를
  표시한다.
- 프로필은 RLS로 본인 행만 조회·수정하며 이메일·역할·상태는 이 화면에서 수정하지 않는다.
- 서버도 이름 2~80자와 새로 입력하는 연락처의 `null` 또는 숫자 10~11자리 규칙을
  강제한다. 검증 추가 전에 저장된 다른 형식의 연락처는 이름만 수정할 때 그대로 보존하고,
  연락처를 직접 수정할 때 현재 형식으로 저장한다.

## 6. 업체 담당자 화면 정의

업체 담당자는 관리자가 업체를 등록할 때 함께 생성한 계정으로 로그인한다. 연결된 업체에
배정된 견적을 조회하고, 상세 확인 후 진행 또는 진행 불가를 서버에 저장한다.

### PAR-001 배정 견적서 확인

| 항목 | 정의 |
|---|---|
| 상태 | `구현` |
| 구현 파일 | `app/(partner)/requests/index.tsx`, `src/features/partner-request-management/` |
| 경로 | `/(partner)/requests` |
| 대상 역할 | 업체 담당자 |
| 목적 | 연결된 업체에 배정된 견적만 상태별로 확인한다. |
| 데이터 | 제한된 Supabase 조회 RPC가 반환하는 현재 업체의 `request_assignments`, `remodel_requests`, 고객 표시명 |
| 주요 표시 | 화면 제목, 4개 상태 탭과 건수, 고객명, 접수일, 지역·상세 주소, 예산, 희망 일정, 상태 |
| 주요 액션 | 상태 탭 선택, 견적 상세 이동, 당겨서 새로고침, 조회 실패 재시도 |
| 필수 상태 | 로딩, 탭별 배정 견적 없음, 조회 오류, 재시도, 새로고침 |

상태 탭:

| 탭 | 포함 조건 |
|---|---|
| `배정 견적` | 현재 업체의 배정 상태가 `assigned`인 견적 |
| `시공중 견적` | 배정 상태가 `accepted`이고 요청 상태가 `in_consultation` 또는 `final_quote_sent`인 견적 |
| `완료 견적` | 배정 상태가 `accepted`이고 요청 상태가 `confirmed` 또는 `closed`인 견적 |
| `취소 견적` | 현재 업체가 `declined`했거나 요청 상태가 `cancelled`인 견적 |

규칙:

- 목록 데이터는 현재 로그인 담당자가 활성 구성원으로 연결된 업체에 배정된 항목만 반환한다.
- 동일 요청이 여러 업체에 배정된 경우 각 업체에는 자신의 배정 응답 상태만 표시한다.
- 클라이언트 탭 라벨인 `시공중 견적`은 별도 DB 상태를 만들지 않고 관리자 `견적 진행`
  탭과 같은 `in_consultation`, `final_quote_sent` 상태를 사용한다.
- 목록 카드는 버튼이며 선택하면 같은 배정의 `PAR-002`로 이동한다.

### PAR-002 견적 상세

| 항목 | 정의 |
|---|---|
| 상태 | `구현` |
| 구현 파일 | `app/(partner)/requests/[requestId].tsx`, `src/widgets/remodel-request-detail/`, `src/features/partner-request-management/` |
| 경로 | `/(partner)/requests/[requestId]` |
| 대상 역할 | 업체 담당자 |
| 목적 | 배정된 고객 견적을 검토하고 진행 가능 여부를 확정한다. |
| 데이터    | Supabase 요청·선택 스냅샷·허용된 고객 표시명과 현재 업체 배정 정보, 요청 단위 전체 상담 타임라인, 상태 전환 RPC             |
| 주요 표시 | 고객 조건, 제품 선택, 조정된 현재 견적 금액과 수정 견적 사유, 배정 정보, 견적 버전, 상담 타임라인 |
| 주요 액션 | 목록 복귀, `견적 확인 및 진행`, `진행 불가`, `시공 완료`                                                                    |
| 필수 상태 | 권한 없음, 로딩, 조회 오류, 배정 대기, 진행 중, 완료, 취소, 저장 중·실패 |

규칙:

- 업체 담당자는 연결된 업체에 배정된 요청만 열람한다.
- 상세 열람 권한이 있는 업체 담당자는 배정 전에 고객·관리자가 남긴 메시지를 포함해 해당
  요청의 전체 상담 타임라인을 고객·관리자와 동일하게 조회한다.
- `견적 확인 및 진행`은 현재 배정이 `assigned`이고 요청이 `matched` 또는
  `in_consultation`일 때만 표시하며, 서버 RPC가 배정을 `accepted`로, 요청을
  `in_consultation`으로 원자적으로 변경한다.
- `진행 불가` 선택 시 `견적을 진행하지 않으시겠습니까?` 확인 메시지를 표시한다.
- 진행 불가 확인 시 현재 업체 배정을 `declined`로 변경한다. 다른 활성 배정이 없을 때만
  요청 전체를 `cancelled`로 변경하며, 다른 업체의 활성 배정은 취소하지 않는다.
- 요청이 `confirmed`, `closed`, `cancelled`인 종료 상태에서는 배정 응답 버튼을 표시하지
  않고 서버도 진행·진행 불가 응답을 모두 거부한다.
- 응답 성공 즉시 목록과 상세 캐시에 새 배정 상태를 반영해 버튼 로딩을 종료하고, 전체 견적
  서버 캐시는 한 번의 백그라운드 재검증으로 갱신한다.
- `시공 완료`는 현재 배정이 `accepted`이고 요청 상태가 `in_consultation` 또는
  `final_quote_sent`일 때만 표시한다. 성공하면 요청을 `closed`로 변경하고 업체 목록의
  `완료 견적` 탭에 포함한다.
- 업체 화면에서는 조정된 금액 바로 아래에 수정 견적 사유를 읽기 전용으로 표시하고, 관리자
  전용 수정 견적 금액·사유 입력과 `견적 조정` 액션은 표시하지 않는다.
- 고객 개인정보는 상담에 필요한 범위만 노출한다.

### PAR-003 견적 작성·수정

| 항목 | 정의 |
|---|---|
| 상태 | `계획` |
| 대상 역할 | 업체 담당자 |

- 연결 완료: 업체명과 로그인 계정 정보를 표시한다.
- 연결 없음: 운영자에게 업체 연결을 요청하라는 안내를 표시한다.
- 조회 오류: 네트워크 확인 안내와 다시 시도를 표시한다.
- 업체 연결이 없거나 조회 중이면 `배정 견적서 확인` 메뉴를 비활성화한다.

## 7. 관리자 화면 정의

관리자는 실제 Supabase 인증 후 관리자 운영 홈에 진입할 수 있다. 견적 옵션 관리와 견적
관리 목록·상세는 실제 Supabase와 연결되어 있다.
과거 로컬 배정 프로토타입은 현재 제거되었으며 `assignment` 경로에는 고객 접근 제한
화면만 남아 있다.

### ADM-001 관리자 운영 홈

| 항목 | 정의 |
|---|---|
| 상태 | `구현` |
| 구현 파일 | `app/(admin)/_layout.tsx`, `app/(admin)/dashboard.tsx` |
| 대상 역할 | 관리자 |
| 목적 | 견적·시공과 운영 기능을 두 섹션으로 구분해 관리 기능과 준비 중인 범위를 안내한다. |
| 데이터 | 인증 세션의 관리자 이름·이메일·역할 |
| 주요 표시 | 관리자 역할 배지, 이름, 이메일, `견적 및 시공 관리`·`운영 관리` 섹션과 3개 메뉴 카드 |

- 기존 `배정 관리` 메뉴는 제거하며, 요청 상세에서의 업체·담당자 배정 계획은 `ADM-003`에 유지한다.

| 액션 | 조건 | 결과 |
|---|---|---|
| 견적 관리 | 항상 | `/(admin)/requests`로 이동한다. |
| 업체 관리 | 항상 | `/(admin)/partners`로 이동한다. |
| 견적 옵션 관리 | 항상 | `/(admin)/catalog`로 이동한다. |
| 로그아웃 | 로그아웃 처리 중이 아님 | Supabase 로그아웃과 보안 저장소 정리 후 로그인 화면으로 이동한다. |

상태:

- 로그아웃 처리 중에는 버튼을 비활성화하고 진행 상태를 표시한다.
- 로그아웃 실패 시 네트워크 확인 안내를 표시한다.
- 이동 가능한 견적 관리, 업체 관리와 견적 옵션 관리 카드에는 상태 배지를 표시하지 않는다.

미구현:

- 전체 요청·매칭·미응답 현황 수치
- 요청 상세에서 업체·담당자 배정

### ADM-002 견적 관리

| 항목 | 정의 |
|---|---|
| 상태 | `부분 구현` |
| 구현 파일 | `app/(admin)/requests/index.tsx`, `src/features/admin-request-management/` |
| 경로 | `/(admin)/requests` |
| 대상 역할 | 관리자 |
| 목적 | 모든 고객이 제출한 요청을 최신순으로 조회하고 DB 상태에 맞는 업무 단계별로 분류한다. |
| 데이터 | Supabase `remodel_requests`, `profiles`, `request_assignments`, `partners` 관리자 조회 결과 |
| 필터 | 상단 5개 상태 탭 |
| 주요 표시 | 화면 설명, 탭별 요청 수, 원본 상태 배지, 고객명, 지역·상세 주소, 예산, 희망 일정, 접수일, 배정 업체 |
| 주요 액션 | 상태 탭 선택, 요청 상세 이동, 당겨서 새로고침, 조회 실패 재시도 |
| 필수 상태 | 로딩, 탭별 검색 결과 없음, 조회 오류, 재시도, 새로고침 |

상태 탭:

| 탭 | 포함하는 `remodel_request_status` | 표시 규칙 |
|---|---|---|
| `신규 견적` | `submitted` | 관리자 배정을 기다리는 제출 요청 |
| `견적 조율` | `quote_adjustment` | 조정 금액과 고객 확인 여부를 카드 배지로 구분 |
| `배정 완료` | `matched` | 업체 또는 담당자가 배정된 요청 |
| `견적 진행` | `in_consultation`, `final_quote_sent` | 원본 상태를 `견적 협의 중`, `최종 견적 도착` 배지로 구분 |
| `완료·종료` | `confirmed`, `closed`, `cancelled`    | 원본 상태를 `최종 컨펌`, `시공 완료`, `취소` 배지로 구분 |

탭 레이아웃:

- 탭 영역은 기기 가로 너비 전체를 사용하며 5개 버튼을 동일한 너비로 배치한다.
- 각 버튼에는 탭 이름과 해당 요청 건수를 두 줄로 표시하고 최소 64px 높이를 확보한다.
- 선택 탭은 옅은 네이비 배경, 진한 네이비 텍스트와 하단 강조선으로 구분한다.
- 탭 바로 아래에는 선택된 목록 이름과 건수를 다시 표시해 탭과 요청 카드 목록이 하나의
  연속된 영역으로 인식되도록 한다.

규칙:

- 탭 분류는 클라이언트 전용 상태를 만들지 않고 DB의 `remodel_request_status` 값을 그대로
  사용한다.
- `draft`는 고객이 제출하지 않은 작성 중 상태이므로 관리자 견적 관리 목록과 탭 건수에서
  제외한다.
- `confirmed`는 계약 또는 시공 완료가 아니며 `closed`와도 의미가 다르므로, 같은 탭에서도
  각각의 원본 상태 배지를 유지한다.
- `cancelled`는 데이터를 삭제하지 않고 취소 이력을 보존하는 종료 상태다.
- 요청 카드는 버튼이며 선택하면 같은 요청 ID의 `ADM-003`으로 이동한다.
- 상태 enum, DB 스키마와 상태 전이 규칙은 별도 사용자 승인 없이 변경하지 않는다.

현재 제약:

- 지역·매칭 업체·생성일의 추가 필터는 계획 상태다.
- 이 화면은 상태를 조회만 하며 상태 변경 기능을 제공하지 않는다.

확인된 요청 처리:

- 견적서 누락 제보는 오류가 아닌 것으로 확인되어 별도 재현·진단·수정 작업을 취소했다.
  카테고리·철거 추가 비용 변경 후 일반 견적 항목·합계 산출은 종합 QA에서 회귀 검증한다.

### ADM-003 관리자 견적 상세·조정

| 항목 | 정의 |
|---|---|
| 상태 | `구현` |
| 구현 파일 | `app/(admin)/requests/[requestId].tsx`, `src/widgets/remodel-request-detail/`, `src/features/update-remodel-request-schedule/`, `supabase/migrations/20260811000100_remodel_request_schedule_changes.sql` |
| 경로 | `/(admin)/requests/[requestId]` |
| 대상 역할 | 관리자 |
| 목적 | 공통 COM-005를 관리자 모드로 열어 고객 요청을 확인하고 초기 견적 금액 조정과 업체 배정을 수행한다. |
| 데이터    | Supabase 요청·일정 변경 이력·선택 스냅샷·고객 프로필·조정 금액·수정 견적 사유·상담 메시지·승인 업체·대표 담당자와 관리자 날짜 변경·조정·배정·시공 완료 RPC; 일정 변경 migration `20260811000100` 원격 적용 완료 |
| 주요 액션 | 목록 복귀, 고객 코멘트 확인, 공사 가능 날짜 선택·저장, 수정 견적 금액·사유 입력, 견적 조정, 업체 배정 모달 열기, 업체 선택·확인·취소, `시공 완료` |
| 필수 상태 | 요청·상담·업체 목록 로딩·오류·없음, 날짜·금액 검증, 날짜 변경·조정·배정·시공 완료 저장 중·실패·완료 |

규칙:

- 요청 상세·제품 선택과 원 견적 합계는 읽기 전용이다.
- 고객이 저장한 요청 단위 코멘트를 상담 타임라인에 생성순으로 표시한다.
- 날짜 섹션 아래와 선택 리포트 위의 `시공 타입` 섹션에서 철거는 제출 시점 추가 비용을 함께
  표시하고 덧방은 타입만 표시한다. 요청별 철거 비용 수정 기능은 제공하지 않는다.
- `submitted` 상태에서만 견적 조정을 실행할 수 있다. `quote_adjustment` 이후에는 수정
  견적 금액·사유 입력과 버튼을 표시하되 비활성화하고, 고객 확인 여부에 맞는 안내를 표시한다.
- 견적 조정 성공 시 목록과 상세 Query를 갱신하고 요청은 `견적 조율` 탭으로 이동한다.
- `업체 배정` 버튼은 견적 조정 섹션 아래에 별도 배치하며 `submitted`,
  `quote_adjustment` 상태에서만 활성화한다.
- 버튼을 누르면 `등록업체 리스트` 모달을 열고 승인된 업체를 업체명과
  `대표담당자이름(이메일)` 두 줄 버튼으로 표시한다.
- 업체 선택 시 `"[업체명] 업체에 견적을 배정하시겠습니까?"` 확인 화면을 같은 모달에서
  표시한다. `취소`는 모달을 닫고, `확인`은 배정 저장을 실행한다.
- 배정 RPC는 관리자 권한, 요청 상태, 승인 업체와 활성 대표 담당자를 재검증한 뒤
  `request_assignments` 생성과 요청 상태의 `matched` 전환을 한 트랜잭션으로 처리한다.
- 배정 RPC 성공 시 모달을 즉시 닫고 `/(admin)/requests`로 교체 이동한다. 관련 Query
  갱신은 화면 이동을 막지 않는 백그라운드 작업으로 실행한다.
- `시공 완료`는 요청이 `in_consultation` 또는 `final_quote_sent`일 때만 표시한다. 공통
  완료 RPC가 관리자 권한과 현재 상태를 재검증한 뒤 요청을 `closed`로 변경하며, 성공하면
  관리자 목록의 `완료·종료` 탭에 포함한다.
- 업체 목록이 비었거나 조회·배정에 실패하면 모달 안에서 안내와 재시도를 제공한다.
- 고객의 `공사 희망 날짜`와 관리자의 `공사 가능 날짜`를 같은 행의 별도 섹션으로 표시한다.
  관리자 입력값이 없으면 공사 가능 날짜 섹션에
  `관리자가 공사 가능날짜를 입력하기 전입니다`를 표시한다. `날짜 입력` 또는 `날짜 변경`으로
  내일 이후 날짜를 선택하고 `변경 저장`을 누르면 관리자 전용 RPC가 사유 입력 없이 저장한다.
  날짜 버튼은 `submitted` 또는 고객 미확인 `quote_adjustment`에서만 표시하며, 고객 확인 완료
  및 이후 견적 단계에서는 표시하지 않고 저장도 실행하지 않는다.
- 서버는 원래 값, 새 날짜, 변경 관리자와 변경 시각을 이력 테이블에 누적하고 성공 후 고객·
  관리자 목록과 상세 Query를 갱신한다. 저장 중에는 중복 입력을 막고 실패 시 선택값을 유지한다.

| 업체 등록 | 필수 입력 6개가 유효하며 등록 처리 중이 아님 | 사업자등록번호·로그인 이메일 중복을 확인하고 업체, Auth 사용자, 대표 멤버 연결과 선택 이미지를 저장한 뒤 업체 목록으로 돌아간다. |

검증과 업무 규칙:

- 입력 항목은 총 8개이며 업체명·사업자등록번호·업체 대표 이메일·패스워드·담당자 이름·담당자 연락처 6개가 필수다.
- 필수 입력이 하나라도 비어 있으면 하단 `업체 등록` 버튼을 비활성화한다.
- 업체 대표 이메일은 이메일 형식을 확인하고 소문자로 정규화한다.
- 패스워드는 고객 회원가입과 동일하게 8자 이상이며 영문 소문자와 특수문자를 각각 하나
  이상 포함해야 한다.
- 비밀번호는 Edge Function에 HTTPS 요청으로 전달해 Auth 사용자 생성에만 사용하며
  폼 입력 중 메모리에만 유지한다. 영구 앱 상태·DB·문서·로그에 저장하거나 응답으로
  반환하지 않는다.
- 사업자등록번호는 하이픈을 제외한 숫자 기준으로 중복만 검사하며 별도 번호 체계 유효성 검사는 하지 않는다.
- 중복이면 `이미 등록된 사업자등록번호예요.`를 표시하고 저장하지 않는다.
- 이미 사용 중인 로그인 이메일이면 `이미 등록된 로그인 이메일이에요.`를 표시하고 저장하지 않는다.
- DB에도 정규화된 사업자등록번호 고유 제약을 적용해 동시 등록 중복을 차단한다.
- 사업자등록증은 JPEG·PNG·HEIC·HEIF 이미지 1장, 최대 10MB로 제한하고 관리자만 접근 가능한 비공개 버킷에 저장한다.
- 생성된 Auth 사용자는 이메일 확인 완료, `partner_staff / active` 프로필로 설정하고 해당
  업체의 활성 대표 멤버로 연결해 즉시 로그인할 수 있게 한다.
- 등록 중에는 모든 입력·첨부·이동·등록 액션을 비활성화해 중복 실행을 막는다.

상태:

- 초기: 빈 폼과 비활성 `업체 등록` 버튼을 표시한다.
- 이미지 권한 거절·선택 실패: 폼을 유지하고 원인을 안내한다.
- 중복 오류: 사업자등록번호 입력 하단에 오류를 표시한다.
- 이메일 중복·비밀번호 정책 오류: 해당 입력 하단에 오류를 표시한다.
- 저장 오류: 입력 내용을 유지하고 화면 상단에 재시도 가능한 오류를 표시한다.
- 저장 성공: 업체 목록 캐시를 갱신한 후 업체 목록으로 교체 이동한다.

- 옵션명은 필수이며 50자 이하, 표시 순서는 1 이상 9,999 이하의 정수다.

- 검증 오류: 해당 입력 아래에 오류 문구를 표시하고 저장하지 않는다.
- 저장 중: 입력·이미지·이동·저장 액션을 비활성화한다.
- 저장 성공: 완료 안내를 표시하고 수정된 값을 유지한다.
- 저장 실패: 입력 내용을 유지하고 재시도 가능한 오류를 표시한다.

현재 제약:

- 신규 마스터 추가·삭제·활성/비활성 전환은 제공하지 않는다.
- 제품은 제품 순서 오름차순으로 표시한다. 같은 순서에서는 생성일시, ID 오름차순으로
  안정적으로 정렬하며 기존 제품의 제품 순서는 모두 `0`으로 초기화한다.
- 고급형 타일 전용 입력 필드는 후속 범위다. 현재 고객 요청 화면은 단순형·고급형 모두 동일한 제품 갤러리로 표시하고 제품별 단가를 합산한다.
- Storage 이미지 변경 권한은 MVP 개발 편의를 위해 인증 사용자 단위로 완화되어 있다.

확인된 요청 처리:

- `수정 후 저장 안 됨` 제보는 오류가 아닌 것으로 확인되어 별도 수정 작업을 취소했다. 향후
  카테고리 전환 작업에서는 현재 `변경사항 저장` 성공·실패·재조회 동작을 회귀 검증한다.

- 기본값과 migration 백필값은 `150`이며 의미는 `150만원`이다. DB 설정과 요청 스냅샷은
  원 단위가 아니라 만원 단위 정수만 저장한다.

- 전역 기본 금액을 변경해도 이미 제출된 요청 스냅샷은 변경하지 않는다.
- 고객이 직접 선택하는 제품 카테고리는 아니지만 관리자가 찾기 쉽도록 `ADM-005` 목록
  최상단의 별도 관리 항목으로 노출한다. `ADM-008` 제품 편집 폼은 재사용하지 않는다.
- 요청별 금액 수정, 활성/비활성 토글과 별도 관리자 홈 메뉴는 제공하지 않는다.

상태:

- 로딩: 설정을 불러오는 중이라는 안내를 표시한다.
- 조회 실패: 네트워크 안내와 `다시 시도`를 표시한다.
- 저장 중: 입력·이동·저장을 비활성화한다.
- 저장 성공: 저장된 금액과 최종 변경 정보를 유지하고 완료 안내를 표시한다.
- 저장 실패: 입력 내용을 유지하고 재시도 가능한 오류를 표시한다.

## 8. 공통 화면·기능 규칙

### 8.1 내비게이션과 권한

- 비로그인 사용자는 보호 화면에 진입할 수 없다.
- 로그인 사용자는 역할에 허용된 화면만 열 수 있다.
- 역할 권한은 화면 숨김만으로 처리하지 않고 서버 데이터 정책과 함께 검증한다.
- 상세 화면에서 대상 데이터가 없거나 권한이 없으면 명시적인 대체 화면을 제공한다.
- Android 고객 홈과 업체 담당자·관리자 홈에서 하드웨어 뒤로가기를 처음 누르면 앱을 종료하지 않고 옅은 네이비 배경의 `한번 더 뒤로가기를 눌러 앱을 종료할 수 있어요` 토스트를 2초 동안 표시한다. 같은 2초 안에 다시 누른 경우에만 앱을 종료하며, 시간이 지나면 다음 입력부터 같은 안내 절차를 다시 시작한다.
- Android 고객의 견적요청·나의견적·알림·설정 탭 최상위에서 뒤로가기를 누르면 홈으로 이동한다. 이 입력은 홈의 종료 대기 첫 입력으로 계산하지 않는다.
- 고객 상세·입력 화면은 직전 화면으로 돌아가고, 직전 화면 이력이 없으면 홈으로 이동한다.
- iOS와 웹의 기존 스택 뒤로가기 동작은 유지한다.

### 8.2 화면 상태

서버 데이터를 사용하는 화면은 다음 상태를 반드시 정의한다.

- 초기 로딩
- 데이터 있음
- 데이터 없음
- 입력 검증 실패
- 네트워크 또는 서버 오류
- 재시도
- 저장 또는 전송 중
- 저장 또는 전송 완료

해당하지 않는 상태는 화면 정의에서 `해당 없음`과 이유를 기록한다.

### 8.3 접근성과 레이아웃

- 모든 화면에 `SafeAreaView` 또는 동등한 안전 영역 처리를 적용한다.
- 모든 터치 요소는 최소 44px 크기를 확보한다.
- 버튼에는 보이는 문구 또는 `accessibilityLabel`을 제공한다.
- 상태는 색상만으로 구분하지 않고 텍스트를 함께 표시한다.
- 처리 중인 버튼은 중복 실행되지 않도록 비활성화한다.

### 8.4 데이터와 보안

- 인증 토큰과 세션은 SecureStore 기반 저장소만 사용한다.
- 화면과 UI 컴포넌트에서 Supabase를 직접 조회하지 않는다.
- 고객 요청·견적·메시지의 서버 연결은 feature repository와 TanStack Query를 사용한다.
- 서비스 역할 키와 비밀값을 앱 번들에 포함하지 않는다.
- 고객 견적 사진은 원격 저장이 제품 범위로 승인되기 전까지 로컬 전용으로 유지한다.
- 업체 사업자등록증은 승인된 범위이며 관리자 전용 비공개 Storage에 저장한다.

### 8.5 브랜드와 고객 하단 내비게이션

- 앱 전반의 메인 컬러는 신뢰형 네이비 팔레트로 전환한다. Primary `#163A63`, Dark
  `#0B1F3A`, Light `#E8EEF6`, Background `#F7F8FA`, Accent `#B86C22`를 사용한다.
- 로고는 밝은 배경에 네이비 버전, 네이비를 포함한 어두운 배경에 흰색 반전 버전을 사용한다.
  임의 색상 변경, 그라데이션과 로고 비율 변형은 허용하지 않는다.
- 기존 성공·경고·오류의 의미는 유지하고, 세부 상태색과 텍스트 명암 대비는 디자인 토큰
  적용 단계에서 접근성 기준과 함께 검증한다.
- 전역 `brand/sand/stone/ink` 토큰을 고객 홈 네이비 팔레트에 연결한다. 브랜드 주 액션과
  아이콘은 Primary/Dark, 앱 배경은 Background, 카드 표면은 흰색, 제목은 Dark, 보조 텍스트는
  비활성 네이비-그레이를 사용한다.
- 성공·경고·오류는 의미 구분과 접근성을 위해 기존 semantic 색상을 유지하고, 색상만으로 상태를
  전달하지 않는 기존 문구·아이콘 규칙을 유지한다.
- 고객 하단 내비게이션은 `견적요청 → 나의견적 → 홈 → 알림 → 설정` 순서로 구현한다.
  `CUS-010`은 중앙 돌출 원형 버튼과 고객 기본 진입 화면이며 Safe Area, 선택 상태와 접근성
  레이블을 반영한다.
- 인증·고객·업체 담당자·관리자 전체 화면은 같은 네이비 토큰을 사용하며 기능, 권한,
  내비게이션과 데이터 흐름은 스타일 전환의 영향을 받지 않는다.

## 9. 화면 변경 관리 절차

### 9.1 구현 전

1. 요청이 영향을 주는 역할과 화면 ID를 찾는다.
2. 기존 목적, 액션, 상태, 권한, 이동 경로와 요청 내용을 비교한다.
3. 정의가 없으면 새 화면 ID와 정의를 먼저 추가한다.
4. 기존 정의와 충돌하면 사용자 결정을 확인하고 문서를 먼저 갱신한다.
5. 구현 대상과 비대상을 확정한다.

### 9.2 구현 후

1. 실제 라우트와 구현 파일을 기록한다.
2. 버튼 문구, 조건, 결과, 이동 경로를 코드와 대조한다.
3. 로딩·빈 상태·오류·완료 상태를 대조한다.
4. 서버 연동인지 로컬 상태인지 정확하게 표시한다.
5. 역할별 화면 요약과 상세 정의를 함께 갱신한다.
6. 문서 검증과 프로젝트 정적 검사를 실행한다.

### 9.3 변경 완료 조건

- 변경된 모든 화면이 이 문서에 반영되어 있다.
- 새 화면에는 중복되지 않는 화면 ID가 있다.
- 모든 실제 화면 파일이 이 문서에서 추적된다.
- 구현하지 않은 기능을 `구현`으로 표시하지 않는다.
- 문서와 코드가 다르면 작업을 완료로 보고하지 않는다.
