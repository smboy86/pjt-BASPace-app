# Maintain Screen Definition

## 기준 문서

`docs/screen-definition.md`를 화면과 기능 결정의 단일 정본으로 사용한다.

- 최상위 화면 분류는 `공통`, `고객`, `업체 담당자`, `관리자` 순서를 유지한다.
- 여러 역할이 재사용하는 화면은 `공통`에 둔다.
- 특정 역할에서만 사용하는 화면은 해당 역할에 둔다.
- 현재 코드와 계획을 섞지 말고 `구현`, `부분 구현`, `로컬 구현`, `계획`, `보류`로 구분한다.
- 기존 PRD, 디자인 문서, spec과 충돌하면 현재 사용자 결정과 실제 코드를 확인하고 이 문서를 갱신한다.

## 작업 절차

### 1. 작업 전 영향 범위 확인

1. `docs/screen-definition.md`를 읽는다.
2. 사용자 요청이 영향을 주는 역할, 화면 ID, 공통 규칙을 찾는다.
3. 관련 Expo Router 화면과 연결된 feature·entity·widget 코드를 확인한다.
4. 다음 변경 여부를 체크한다.
   - 화면 추가·삭제·이름 변경
   - 버튼·입력·선택 요소 변경
   - 버튼 활성 조건과 결과 변경
   - 역할과 접근 권한 변경
   - 진입·이탈·딥링크 경로 변경
   - 로딩·빈 상태·오류·완료 상태 변경
   - 서버 연동과 로컬 상태 경계 변경
5. 정의가 없거나 사용자 요청과 충돌하면 구현 전에 문서를 먼저 수정한다.

사용자 결정이 필요한 제품 동작을 추측하지 않는다. 구현 방향을 바꾸는 모호성이 있으면
선택지를 설명하고 확인한다.

### 2. 화면 정의 작성

새 화면은 다음을 모두 기록한다.

- 중복되지 않는 화면 ID
  - 공통: `COM-NNN`
  - 고객: `CUS-NNN`
  - 업체 담당자: `PAR-NNN`
  - 관리자: `ADM-NNN`
- 화면명, 경로, 상태, 대상 역할
- 목적, 진입 조건, 이탈 경로
- 구현 파일과 사용하는 데이터
- 주요 표시 정보
- 버튼·액션의 조건과 결과
- 입력 검증과 업무 규칙
- 로딩·빈 상태·오류·완료·권한 제한 상태
- 현재 제약과 미구현 범위

요약 표와 상세 정의를 함께 갱신한다. 화면 구현 전이면 예정 경로와 `계획` 상태를 사용하고,
구현 후 실제 경로와 구현 파일로 교체한다.

### 3. 코드 구현

화면정의서 범위 안에서 구현한다. 작업 도중 정의 변경이 필요해지면 코드만 우회 수정하지
말고 문서를 먼저 또는 같은 변경 세트에서 갱신한다.

### 4. 구현 후 대조

다음을 실제 코드와 한 항목씩 대조한다.

- 버튼의 보이는 문구와 접근성 레이블
- 버튼의 활성·비활성 조건
- 입력값과 검증
- 상태별 문구와 재시도
- 실제 내비게이션 경로
- 역할별 노출과 서버 권한
- Supabase·TanStack Query·Zustand 등 데이터 출처
- 성공 동작의 실제 저장 여부

프로토타입이나 메모리 상태를 서버 저장으로 표현하지 않는다. 정상 UI 흐름으로 도달할 수
없는 화면 상태나 버튼이 있으면 현재 제약에 기록한다.

### 5. 검증

화면 파일 추적과 필수 문서 구조를 검사한다.

```bash
node .agents/skills/maintain-screen-definition/scripts/validate-screen-definition.mjs
```

코드 변경이 있으면 프로젝트 기준에 따라 다음도 실행한다.

```bash
npm run typecheck
npm run lint
```

### 6. 완료 보고

다음을 포함한다.

- 영향을 받은 화면 ID
- 문서에서 변경한 정의
- 실제 구현과 데이터 연동 수준
- 실행한 검증과 결과
- 남은 `계획`, `부분 구현`, `보류` 항목

문서와 코드가 다르면 작업을 완료로 보고하지 않는다.
